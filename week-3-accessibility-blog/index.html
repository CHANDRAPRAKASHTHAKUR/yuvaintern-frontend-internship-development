Designing interfaces that work for everyone

Roughly one in six people live with a disability that affects how they use the web. Accessibility is not a special mode bolted on at the end — it is a set of engineering decisions that make the product better for everybody. Here is the checklist we actually use.

Written by Aisha Mensah, Principal accessibility engineer

Start with the semantics

The cheapest accessibility fix is the one you never have to write: letting the browser do the work. A <button> is focusable, activatable with both Enter and Space, and announced as a button. A <div onclick> is none of those things, and fixing it later means adding a tabindex, two key handlers and a role — at which point you have spent more code than the semantic element would have cost.

Landmarks first

Screen-reader users navigate a page by landmark, not by scrolling. Every page should expose at least banner, navigation, main and contentinfo. On this site that means <header>, <nav aria-label="Main">, <main> and <footer>. Multiple navigation landmarks must be given unique aria-labels — a screen reader that finds three landmarks all called “navigation” is no help at all.

Rule of thumb

If you can delete a wrapper <div> and nothing changes visually, it should be a <section> with an accessible name — or nothing at all.

One h1, then never skip a level

Heading levels are the table of contents that assistive technology builds for you. Jumping from h2 to h4 breaks the outline, and choosing a level for its font size rather than its meaning is the single most common heading bug in production code. This article has exactly one h1, and every section heading is an h2 with subsections at h3.

Keyboard is a feature, not a fallback

Every interaction must be possible with a keyboard alone. That means a visible focus indicator, a logical tab order that follows the visual order, and a focus style that survives on coloured backgrounds. We use :focus-visible rather than :focus so mouse users do not see rings on every click, and we never remove an outline without replacing it.

Tables need <caption> and scope on every header cell; without them a screen reader announces column numbers instead of names.

Managing focus in dialogs

When a dialog opens, focus moves into it and stays there. Tab cycles inside the dialog, Esc closes it, and focus returns to the exact control that opened it. The rest of the page is hidden with aria-hidden="true" so nothing behind the dialog is reachable. Press ? or use the button below to try it.

Contrast and colour

WCAG 2.1 AA requires a contrast ratio of at least 4.5:1 for normal body text, 3:1 for large text (24 px, or 18.66 px bold) and for the boundaries of user-interface components. Our original palette used a slate grey of #8b93a7 on white at 2.9:1 — it failed, and the fix was simply to darken it to #4a5169 (7.6:1).

Colour is never the only signal. The status badges below use an icon and a text label alongside the colour, so they still work for someone who cannot distinguish red from green.

Watch out

Placeholder text is still text. Chrome renders ::placeholder at 54% of the inherited colour, which silently drops a grey placeholder below the contrast threshold. Always set an explicit placeholder colour and keep the label visible.

Respect motion preferences

Animation can trigger nausea, dizziness and migraines for people with vestibular disorders. A single media query handles the whole page: 

@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.001ms !important;
    transition-duration: 0.001ms !important;
    scroll-behavior: auto !important;
  }
}

We also avoid parallax and auto-playing video entirely, and any animation over 5 seconds can be paused. The reading-progress bar at the top of this article is decorative, so it is hidden from assistive technology with aria-hidden="true".

Forms that explain themselves

Every input needs a real <label>; placeholders are not labels because they disappear the moment someone types. Errors must be described in text, tied to the field with aria-describedby, and announced — a role="alert" paragraph is the simplest reliable way. Required fields are marked with a word, not only an asterisk.

How we test

Automated tools catch roughly a third of accessibility defects — missing labels, broken contrast, absent landmarks. The rest needs a human. Our loop is:

  1. Automated — Lighthouse and axe run on every pull request and block the merge.
  2. Keyboard only — unplug the mouse and complete the primary task.
  3. Screen reader — NVDA with Firefox and VoiceOver with Safari, at least once per release.
  4. Zoom and reflow — 200% browser zoom and 320 px width with no horizontal scrolling (WCAG 1.4.10).
  5. People — quarterly sessions with users who rely on assistive technology.

The audit that produced this page is documented in AUDIT-REPORT.md, with each issue, its WCAG success criterion, the technique used and the manual test that verifies the fix.

Common questions

Is accessibility expensive?

Fixing a defect during design costs a fraction of fixing it after launch. Retrofitting is where projects get expensive.

Which tools should I use?

Lighthouse and axe-core for automation, then NVDA, VoiceOver and a physical keyboard for everything else.

Do I need a full audit every release?

An automated pass on every pull request plus a manual review before a major release is a sustainable minimum.
